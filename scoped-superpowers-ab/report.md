# Scoped Superpowers를 명시하면 토큰과 시간이 얼마나 달라질까?

2026-09-08, 같은 정산 코드 감사 과제를 새 Codex 세션으로 A/B 각 3회 실행했다. **이번 과제에서는 scoped Superpowers를 명시한 B의 중간 입력 토큰이 35.2%, 출력 토큰이 21.1%, 경과 시간이 26.2% 더 많았다.** 정답률은 양쪽 모두 3/3이었다.

이는 한 가지 읽기 전용 과제에서 확인한 추가 비용이다. 일반적인 개발 작업에서 scoped Superpowers가 항상 느리다거나 토큰을 절약하지 못한다는 결론은 아니다.

## 무엇을 비교했나

| 조건 | 고정값 |
| --- | --- |
| 실행 도구 | Codex CLI 0.153.4 |
| 모델 / reasoning | `gpt-5.6-sol` / `medium` |
| 과제 | 합성 정산 코드의 계약 위반 3개와 정확한 집계값 찾기 |
| 초기 파일 | 동일 AGENTS·계약·Python 코드·16개 이벤트·동결 workflow |
| 출력 | 동일 JSON schema, 계정별 금액·전체 합계·결함 목록 |
| 실행 | 새 `codex exec`, ephemeral, read-only, 순차 실행 |
| 반복 | A 3회, B 3회; AB / BA / AB |
| A | scoped Superpowers와 bundled reference 사용 금지 |
| B | scoped Superpowers와 verification-before-completion 사용 명시 |

공통 프롬프트는 두 arm 모두 새 로컬 증거로 답을 검증하도록 요구한다. 마지막 workflow 선택 문장만 다르다. 따라서 **검증을 하는 모델과 하지 않는 모델의 비교가 아니라, 명시적인 workflow 지침이 더해졌을 때의 차이**를 본다.

실제 설치된 rv-workflow의 router·routing·완료 검증 문서를 동결해 양쪽에 동일하게 제공했다. B에서는 세 문서를 읽은 command와 정상 종료가 관측됐고, A에서는 workflow 읽기가 관측되지 않았다. 별도 Superpowers 플러그인은 설치하지 않았다. 전체 플러그인의 설치 유무나 모든 Superpowers workflow를 비교한 실험은 아니다.

설치 메타데이터는 `0.1.0+codex.20260905125105`, 같은 경로의 package.json은 `0.1.1`이었다. 실제 사용한 내용은 [환경 정보](./environment.json)와 [fixture 해시](./results/campaign-01/protocol.json)로 식별한다.

## 중간값과 범위

괄호는 최소~최대다. 차이는 **B 중간값 − A 중간값**, 백분율은 그 차이를 A 중간값으로 나눈 값이다.

| 지표 | A: 사용 안 함 | B: 사용 명시 | 절대 차이 | 차이율 |
| --- | ---: | ---: | ---: | ---: |
| input tokens | 65,388 (65,376~83,193) | 88,429 (71,263~88,618) | +23,041 | +35.24% |
| cached input tokens | 47,488 (47,488~64,640) | 51,328 (49,536~83,072) | +3,840 | +8.09% |
| output tokens | 1,093 (1,030~1,345) | 1,324 (1,323~1,476) | +231 | +21.13% |
| reasoning output tokens | 261 (116~285) | 416 (333~450) | +155 | +59.39% |
| total tokens | unavailable | unavailable | unavailable | unavailable |
| wall time | 52.35초 (49.84~64.21) | 66.06초 (62.87~70.83) | +13.70초 | +26.18% |
| 정답 | 3/3 | 3/3 | 0건 | 0%p |
| 정상 종료 | 3/3 | 3/3 | 0건 | 0%p |

`turn.completed.usage`가 반환한 `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`를 그대로 사용했다. `total_tokens`는 노출되지 않아 계산으로 채우지 않았다. cached input을 input에 더하거나 reasoning을 output에 더해 별도 총량을 만들지도 않았다. 이 표는 요금 계산표가 아니다.

wall time은 Codex 프로세스 실행 직전부터 반환까지 측정했다. CLI 시작·모델 요청과 대기·도구 실행·최종 출력이 모두 포함되며, 서버의 순수 추론 시간은 분리하지 못한다.

## 무엇까지 말할 수 있나

이번 조건에서는 검증 절차를 이미 요구한 과제에 scoped workflow를 명시적으로 더했을 때, 정답률의 차이 없이 토큰과 시간이 증가했다. B의 문서 읽기와 실행 경로가 추가 비용의 후보이지만, 문서 길이·명시 문장·도구 선택 각각의 기여를 분리해 추정한 것은 아니다.

다음 한계가 남는다.

- **과제와 표본:** 합성 코드 감사 한 종류, arm당 3회다. A도 모두 정답이라 품질 향상이 드러날 여지가 작다. 긴 구현·불명확한 디버깅·실패 복구에는 일반화할 수 없다.
- **캐시:** 세션과 파일 상태는 새로 시작했지만 제공자 측 prompt cache를 비우거나 고정하지 않았다. cached input이 크게 달라 cold-cache 실험이라고 부를 수 없다.
- **외부 실행 상태:** 서비스 부하, 네트워크, 호스트의 다른 프로세스, 연구 소유 세션의 활동을 완전히 통제하지 않았다. wall time에는 이 영향이 포함된다.
- **모델 재현성:** 같은 모델 이름·reasoning을 요청했지만 hosted 모델의 내부 build·sampling seed는 고정하거나 확인하지 못했다. 재현 명령은 조건을 재현하며 동일한 수치를 보장하지 않는다.
- **적용 범위:** `--ignore-user-config`와 study 밖의 동일 임시 workspace로 프로젝트 설정 차이를 줄였다. 측정 대상은 동결한 scoped 문서의 명시적 적용이며, 일상적인 플러그인 자동 발견·study startup·progress UI까지 포함한 전체 경험의 비교가 아니다. auth와 기존 study 과제를 대상으로 실행하지 않았다.
- **준수 확인:** 성공한 파일 읽기 command는 적용 지시 이행의 관측 근거다. 모델이 내부적으로 모든 절차를 따랐는지는 알 수 없다. A 역시 학습된 일반 검증 지식을 사용하지 못하게 할 수는 없다.
- **계측 보정:** 첫 실제 usage에서 reasoning 키 이름을 확인하고 정규화기를 보정했다. 프롬프트·fixture·실행 조건은 유지했으며 원래 usage를 보존했다. 스키마 확인까지 사전 등록된 연구는 아니다.

후속 실험을 한다면 과제 난이도와 유형을 늘리고, 동일 과제군에서 더 많은 균형 교차 반복과 품질 채점을 먼저 정해야 한다. 이번에는 추가 과제나 재측정을 수행하지 않았다.
