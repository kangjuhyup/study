# 작은 코드 변경에 Superpowers는 과했다

간단한 코드 변경을 맡겼는데, 에이전트가 설계와 계획부터 시작했다. Superpowers를 적용한 Codex를 사용하면서 겪은 불편이다. 전체 개발 절차를 요청하지 않아도 작은 수정이 큰 작업처럼 진행되는 경우가 있었다.

워크플로우 없이 맡길 때도 문제는 있었다. 작업 방식과 결과물의 일관성이 부족했고, 품질도 기대에 못 미쳤다. 기준은 필요했지만, 이미 수정할 내용이 명확한 작업까지 긴 절차를 거치는 것은 과하다고 느꼈다.

그래서 작업 크기와 위험에 따라 필요한 절차를 고르는 workflow를 직접 만들었다. 이번에는 그 선택을 숫자로 확인해 봤다. 작은 함수 변경을 비교한 결과, **Superpowers는 직접 구현보다 입력 토큰을 약 2.11배 사용하고 약 51초 더 걸렸다.** 최종 코드는 모두 같은 테스트를 통과했지만, 검증 과정에는 차이가 있었다.

## 작은 요청에 절차가 붙는 이유

Superpowers에서는 에이전트가 스킬 문서를 읽으며 작업 방식을 결정한다. 시작점인 `using-superpowers`는 응답이나 작업 전에 관련 스킬을 확인하도록 요구한다. 적용 가능성이 조금이라도 있으면 먼저 읽는 쪽으로 강하게 유도한다. [진입 지침](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/using-superpowers/SKILL.md)

그다음에는 각 스킬의 조건을 따른다. 기능이나 동작을 바꾸는 작업에는 테스트를 먼저 작성하는 **TDD**가, 완료를 보고할 때는 검증 지침이 적용된다. 여러 스킬이 해당하면 설계나 원인 조사처럼 접근 방식을 정하는 스킬을 먼저 사용한다.

스킬 안에서도 작업을 나눈다. 브레인스토밍의 경우 기존 코드의 한정된 변경은 짧은 설계를 대화로 확인하고, 구조를 바꾸는 작업은 설계 문서와 구현 계획으로 이어진다. 절차는 에이전트가 선택하지만, 관련 지침을 생략하지 않도록 규칙이 강하게 작용하는 구조다. [작업 규모별 경로](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/skills/brainstorming/SKILL.md)

이 구조라면 단순한 수정 요청에도 절차가 추가될 수 있다. 그 비용을 확인하기 위해, 전체 워크플로우를 지시하지 않고 같은 짧은 요청만 보내기로 했다.

## 같은 함수, 같은 요청으로 비교했다

과제는 기존 태그 정리 함수의 동작을 바꾸는 것이었다.

> 기존 normalize_tags에서 lower() 대신 casefold()를 사용하고, 정규화한 태그의 중복을 첫 등장 순서대로 제거해 주세요. 기존 입력 검증은 유지하고 관련 테스트를 추가해 실행해 주세요.

별도 workflow 없이 직접 구현하는 환경, Superpowers를 따르는 환경, 직접 만든 workflow의 **scoped 규칙**으로 절차를 고르는 환경을 비교했다. 개인 workflow 전체를 평가한 것은 아니다.

모델은 `gpt-5.6-sol`, reasoning은 `medium`으로 고정했다. Superpowers는 **[6.3.0 소스](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/.claude-plugin/plugin.json), 커밋 [b36e0829c6d0](https://github.com/obra/superpowers/commit/b36e0829c6d0140e93cfef2ca599b1b07d4a7797)**를 사용했다. 설치된 플러그인을 켜고 끄는 대신, 고정한 스킬 문서를 읽고 따르게 했다.

매번 같은 초기 코드와 새 세션에서 시작했다. 실행 순서를 교차하며 각각 세 번 측정했고, 에이전트가 작성한 테스트와 별개로 준비한 14개 테스트로 결과를 채점했다. 아래 수치는 세 번 실행의 중간값이다.

| 지표 | 직접 구현 | Superpowers | 개인 workflow |
| --- | ---: | ---: | ---: |
| 입력 토큰 | 109,956 | 232,127 | 82,776 |
| 출력 토큰 | 1,550 | 2,544 | 1,474 |
| 소요 시간 | 74.27초 | 125.46초 | 71.71초 |
| 별도 14개 테스트 통과 | 3회 모두 | 3회 모두 | 3회 모두 |

Superpowers는 직접 구현보다 입력 토큰 111.1%, 출력 토큰 64.1%, 시간이 68.9% 더 들었다. 입력에는 캐시된 토큰도 포함되므로, 이 비율이 그대로 요금 증가율을 뜻하지는 않는다.

개인 workflow는 Superpowers보다 약 54초 적게 걸렸고, 직접 구현과는 비슷한 시간에 끝났다. 추가 절차를 줄인 효과는 보였지만, 최종 정답률만으로는 세 방식의 차이를 설명할 수 없었다.

## 추가 비용으로 얻은 것은 검증 근거였다

실행 기록을 보면 Superpowers는 세 번 모두 TDD와 완료 검증 지침을 읽고 다음 순서로 작업했다.

| 방식 | 실제 테스트 과정 |
| --- | --- |
| 직접 구현 · 개인 workflow | 구현 → 테스트 통과 확인 |
| Superpowers | 테스트 실패 확인 → 구현 → 통과 확인 → 최종 재검증 |

변경 전 코드에서 새 테스트가 실패하고, 변경 후에는 통과했다. 이는 **추가한 테스트가 요청한 동작 차이를 실제로 감지한다는 근거**다. 실패를 먼저 확인하는 단계에는 분명한 가치가 있었다. 세 번 모두 같은 검증 절차를 수행했다는 점도 Superpowers의 이점이었다.

그 대가로 지침을 읽고 검증 단계를 수행하는 토큰과 시간이 더 들었다. 이번처럼 범위가 명확한 과제에서는 그 비용에 상응하는 최종 정답률 차이를 확인하지 못했다. 작은 작업에도 이런 절차를 기본으로 적용하는 것이 과하다고 판단한 이유다.

다만 이번 실행에서 설계·계획 문서까지 만들지는 않았다. 처음 겪었던 긴 워크플로우 전체를 재현한 결과는 아니다. 측정한 차이를 TDD 한 단계의 비용으로 분리할 수도 없다. 스킬 읽기와 도구 실행 등을 포함한 작업 전체의 차이다.

## 기준은 남기고, 절차를 선택하게 했다

직접 만든 workflow에서는 먼저 변경의 크기와 위험을 판단하게 했다. 범위가 명확하면 수정과 필요한 테스트로 끝낸다. 요구사항이 모호하면 설계를, 원인이 불분명하면 조사를 먼저 한다. 범위가 넓거나 위험한 변경에는 계획과 리뷰를 더한다.

워크플로우 없이 맡겼을 때 느낀 일관성과 품질의 부족, Superpowers를 적용했을 때 겪은 과도한 절차를 함께 줄이려는 선택이었다. 이번 작은 과제에서는 테스트 통과를 유지하면서 토큰과 시간을 줄일 수 있었다.

절차를 덜 수행한 만큼 포기한 근거도 있다. 개인 workflow에서는 변경 전 테스트 실패를 확인하지 않았다. 작업의 위험을 낮게 판단하면 필요한 검증까지 빠뜨릴 수 있으므로, 비용이 적다는 이유만으로 더 좋은 workflow라고 결론 내릴 수는 없다.

이번 실험으로 확인한 것은 작은 작업에서 절차를 제한할 여지가 있다는 점이다. 평소 느꼈던 일관성과 품질의 차이, 복잡한 작업에서 설계와 리뷰가 주는 효과는 별도로 확인해야 한다.

앞으로는 **중간 규모와 대규모 작업에서도 효율을 측정할 예정**이다. 토큰과 시간에 결과물의 품질을 함께 놓고 비교하면서, 어느 작업에 어느 정도의 절차가 필요한지 기준을 다듬으려고 한다.
