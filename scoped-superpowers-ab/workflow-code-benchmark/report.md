# 간단한 코드 변경에서 Superpowers가 스스로 선택한 절차와 비용

2026-09-08 같은 한 문장의 코드 변경 요청을 A/B/C 환경에서 각각 새 세션으로 3회 실행했다. **개인 scoped(C)는 일반 Superpowers(B)보다 중간값 기준 input 64.34%, output 42.06%, 경과 시간 42.84%가 적었다.** 독립 채점은 세 환경 모두 3/3 통과했다.

사용자가 전체 workflow를 요구하지 않았는데 에이전트가 자동으로 절차를 추가하는 현상을 관찰하는 실험이다. **계획서 작성까지 이어지는 전체 단계 확장은 재현되지 않았다.** 일반 Superpowers가 TDD·완료 검증 지침을 읽고 RED→GREEN 및 재검증을 수행한 점은 관측됐다.

## 비교 조건

| 항목 | 설정 |
| --- | --- |
| 모델 / reasoning | gpt-5.6-sol / medium |
| 도구 / 런타임 | Codex CLI 0.153.4 / Python 3.10.15 |
| 사용자 요청 | 기존 함수의 lower를 casefold로 변경, 정규화 후 순서 보존 중복 제거, 기존 검증 유지, 테스트 추가·실행 |
| 초기 상태 | 동일한 동작 중 코드와 계약, 동일한 workflow 파일들, 동일 JSON 출력 schema |
| A | workflow 없이 직접 수행 |
| B | 일반 Superpowers using-superpowers 진입 정책; 이후 단계 자율 선택 |
| C | 개인 rv-workflow scoped 진입 정책; 이후 단계 자율 선택 |
| 순서 | seed 20260908, BCA / CAB / ABC |
| 세션 | 매번 새 exec, ephemeral, ignore-user-config, 같은 임시 경로에 초기 파일 복원 |
| 채점 | 모델 외부의 14개 unittest 메서드, 보호 파일·허용 쓰기 범위 확인 |

사용자 프롬프트 세 파일은 바이트까지 같다. AGENTS의 workflow 구성 부분만 달라진다. 같은 초기 파일 해시와 arm별 설정 해시를 확인했다. B에 특정 스킬이나 계획 문서 생성을 지시하지 않았다. C에 small 판정을 강요하지 않았다.

B는 upstream revision `b36e0829c6d0140e93cfef2ca599b1b07d4a7797`의 skills를 동결했고, C는 앞선 연구에서 동결한 rv-workflow scoped router를 사용했다. 파일 읽기를 Skill loader에 대응시키는 통제 환경이다. 플러그인 설치 유무 자체나 전체 RV Workflow 기능을 비교한 것은 아니다.

해당 upstream 커밋의 [plugin manifest](https://github.com/obra/superpowers/blob/b36e0829c6d0140e93cfef2ca599b1b07d4a7797/.claude-plugin/plugin.json)에 선언된 Superpowers 버전은 **6.3.0**이다. 재현 기준은 버전명과 위 전체 커밋 해시를 함께 사용한다.

사람 승인 대기·subagent·Git 변경·네트워크·서비스·의존성 설치는 제외했다. 계약 범위 내 결정은 공통으로 사전 승인했고, 필요 시 리뷰는 자기검토로 수행하도록 했다. 이 조건은 실제 대화형 사용과 차이가 있다.

`turn.completed.usage`에 노출된 필드만 기록했다. total은 노출되지 않아 unavailable이다. input과 cached, output과 reasoning을 더해 총량을 만들지 않았다. cached로 보고된 입력이 많으므로 이 수치를 요금 절감률로 바꿔 읽지 않는다.

시간은 CLI 프로세스 실행 직전부터 반환까지의 wall time이다. 모델 요청·대기·파일 읽기·도구 실행이 포함되며, 독립 채점 시간은 제외한다.

## 실제로 선택한 절차

| 관측 | A | B | C |
| --- | --- | --- | --- |
| workflow 진입 문서 | 없음 | using-superpowers, 3/3 | scoped router, 3/3 |
| brainstorming 읽기 | 없음 | 1/3 | 없음 |
| TDD 지침 읽기 | 없음 | 3/3 | 없음 |
| 완료 검증 지침 읽기 | 없음 | 3/3 | 없음 |

| unittest 실행 횟수, 각 반복 | 1 / 1 / 1 | 3 / 3 / 3 | 1 / 1 / 1 |
| command 호출 수, 각 반복 | 3 / 4 / 4 | 7 / 6 / 7 | 3 / 2 / 3 |
| 독립 14개 테스트 통과 | 3/3 | 3/3 | 3/3 |

B는 TDD의 의도된 실패를 확인한 뒤 구현했고, 통과 후 다시 검증했다. A와 C는 구현·테스트를 작성한 다음 검사했다. 모든 최종 함수는 독립 테스트를 통과했다. 테스트 실행 횟수가 많다는 사실 자체를 낭비라고 정의하지 않는다.

스킬 파일을 읽은 사실과 모든 스킬 절차를 수행한 사실도 구분한다. brainstorming은 B 첫 실행에서 읽혔지만 설계·계획 파일이 만들어지지는 않았다. 따라서 이번 비용을 “브레인스토밍→계획→검증→TDD→QA 전체 사슬의 비용”으로 이름 붙일 수 없다.

[process.json](./results/autonomous-01/process.json)의 관측은 command·파일 변경 이벤트에서 도출했다. 테스트 command 뒤에 `&& git diff` 등이 붙어 전체 shell은 실패했지만 unittest는 OK인 경우가 있다. 이 때문에 shell 종료 코드와 테스트 출력 판정을 분리했다. 저장한 [최종 구현·테스트](./results/autonomous-01/)로 독립 채점도 다시 재현했다.

## 개인 workflow를 만든 이유에 대한 해석

이번 결과는 **작은 변경에서 기본 절차의 비용을 줄이는 scope gate가 유용할 수 있다**는 제한된 근거다. B는 더 많은 스킬과 검증 단계를 선택했고 토큰·시간이 더 들었다. C는 router만 읽고 직접 구현에 가까운 절차로 마쳤다. 정해 둔 독립 채점에서는 최종 정답률 차이가 없었다. 다만 B에는 변경 전 실패 확인이라는 추가 검증 근거가 남았으므로, 이를 포함한 모든 절차의 가치를 정답률 하나로 평가하지 않는다.

반면 C는 A보다 항상 빠르지 않았다. 따라서 이 사례가 지지하는 설명은 “개인 workflow가 Codex 자체를 더 똑똑하게 만든다”가 아니라 **범용 지침이 작은 과제에 추가하는 절차를 선택적으로 제한한다**는 것이다. 검증은 유지하면서, 문제의 규모와 위험에 맞는 절차를 고르는 것이 설계 목적이다.

사용자가 겪었던 전체 계획 절차로의 확대 해석은 경험 서술로 남길 수 있지만, 이번 9회 측정으로 입증됐다고 쓰면 안 된다. 당시의 정확한 버전·프로젝트 규칙·대화 맥락까지 동일하게 복원한 연구가 아니다.

## 한계와 후속 검증

- **작은 표본과 한 과제:** arm당 3회, 기존 함수 하나다. 모든 답이 채점을 통과한 결과가 장기 유지보수성·다른 경계 사례·복잡한 구현의 품질까지 같다는 뜻은 아니다.
- **Git 없는 fixture:** 모든 실행에서 Git 조회 또는 diff 관련 실패가 있었다. 일부 `git diff`는 저장소 밖에서 두 파일 비교로 해석됐다. 환경은 공통이지만 오류 대응이 workflow별 비용에 영향을 줬다. 일반 Git 프로젝트에 그대로 적용할 비율이 아니다.
- **캐시·모델 비결정성:** 새 세션과 초기 파일은 같아도 제공자 cache·sampling·backend build·부하를 고정하지 못했다. first-arm 무작위화와 위치 균형은 직전 실행의 모든 잔류 효과를 없애지 못한다.
- **wall time 범위:** 네트워크와 호스트의 다른 활동이 포함된다. 순수 모델 연산 시간이나 사람이 승인하는 시간은 측정하지 않았다.
- **일부 운영 경로 제외:** subagent 리뷰·worktree·commit·실제 plugin discovery 전체를 포함하지 않는다. 공개 source를 loader에 대응시킨 정책 실험이다. 설치 제거로 기본 컨텍스트가 달라지는 효과를 측정한 것은 아니다.
- **원인 분해 없음:** 문서 읽기, TDD, 재검증, 오류 복구 각각의 기여를 따로 무작위화하지 않았다. 전체 차이를 한 단계 탓으로 돌리지 않는다.

후속 검증에는 Git 저장소 fixture, 더 많은 독립 과제와 반복, 실제 대화 승인 경로가 필요하다. 이 결과만으로 모든 Superpowers 사용을 낭비라고 결론 내리지 않는다.

## 연구 기록과 보존

[protocol.md](./protocol.md)에 재현 조건과 첫 강제 절차 파일럿을 중단한 이유를 남겼다. 그 파일럿은 사용자 정정 전에 시작한 별도 실행이며 본 비교에 포함하지 않았다. 완료 usage가 없어 해당 토큰과 정확한 wall time은 unavailable이다.

[README](./README.md)의 run/analyze/inspect_process/verify 명령으로 새 디렉터리에 재현할 수 있다. 독립 grader는 초기 구현을 거부하고 reference 구현을 통과시키는 것으로 사전 확인했다. 최종 9개 산출물에서도 14개 테스트 통과를 재현했다. 사전 채점 중 생긴 Python bytecode cache는 소스 해시에서 제외됐고 실행 중 완전히 통제하지 못했다. 보관본에서는 생성된 cache를 제거했다. 재현 실행기는 복사 시 cache를 제외하고 grader에 `-B`를 사용한다. 사용자 요청·workflow·소스·모델 명령은 동일하지만, 과거 실행의 bytecode cache 상태까지 재현하는 것은 아니다.

연구 작성 당시 기존 Refresh 변경과 앞선 A/B 자료는 파일 해시로 보존을 확인했다. 이후 사용자 요청에 따라 2026-09-09 블로그 원고를 공개 대상으로 등록했다. 원시 측정 자료는 변경하지 않았다.
